# law-api — 법제처 법령정보 Open API 수집 (6주차 실습)

법제처 국가법령정보 Open API로 **법령 검색(법령ID 획득) → 본문조회 → 재사용 함수 → FastAPI 서버 → SQLite 캐시**까지 이어지는 수집 파이프라인.

## 파일 구성

| 파일 | 역할 |
|---|---|
| `step1_search.py` | 목록조회(`lawSearch.do`)로 법령 검색 → 법령ID 출력 |
| `step2_detail.py` | 본문조회(`lawService.do`)로 법령ID의 현행 조문 출력 |
| `law_client.py` | `search_law` · `get_law_detail` 재사용 함수 (인증키는 `.env`에서 읽음) |
| `explore.py` | 응답 JSON을 들여쓰기로 출력해 구조 확인 |
| `main.py` | FastAPI 서버 — `/search`, `/detail/{law_id}` (DB 캐시 포함) |
| `db.py` | SQLite(`law.db`) 테이블 생성·저장·조회 |

실행: `.env`에 `LAW_OC=본인OC` 한 줄을 넣고 `uvicorn main:app --reload` → `http://127.0.0.1:8000/docs`

## ① 결과 확인

- 검색: `search_law("전자금융거래법")` → `전자금융거래법(010199)`, `전자금융거래법 시행령(010366)` 2건
- 본문: `get_law_detail("010199")` → 조문 80건 (`제1장 총칙`, `제1조(목적) …`, `제2조(정의) …` 순)
- 서버: `/search?query=전자금융거래법` → `{"count": 2, …}`, `/detail/010199` → `{"article_count": 80, …}`, `/docs`에 두 엔드포인트 표시
- 캐시: `/detail/010199`를 두 번 호출 → 1차 `"source": "api(law.go.kr)"`, 2차 `"source": "db(cache)"`(`fetched_at` 포함)로 바뀜
- 오류 처리 확인
  - 잘못된 OC → `호출 실패: 사용자 정보 검증에 실패하였습니다.`
  - 법령일련번호(290247)로 본문조회 → `조회 실패: 일치하는 법령이 없습니다.`
  - `.env` 없음 → `.env에 LAW_OC=내OC 한 줄을 넣어주세요`

## ② 핵심 개념 되새김

- **인증키(OC)**: 법제처가 "누가, 어느 IP에서" 호출하는지 확인하는 신분증이다. API 서버는 요청 하나하나를 따로 처리하고 이전 요청을 기억하지 않으므로, 요청할 때마다 키를 붙여야 한다. 키는 `.env`에 두고 `.gitignore`로 커밋에서 뺐다.
- **목록조회 → 상세조회 2단 호출**: 목록조회는 키워드로 법령을 찾아 법령ID 같은 요약 정보만 돌려주고, 본문(조문)은 주지 않는다. 그래서 법령ID를 얻은 뒤 본문조회를 한 번 더 호출해야 한다. 법령ID는 개정돼도 바뀌지 않으므로 본문조회에 넣으면 늘 현행본이 온다. 법령일련번호(MST)는 개정본마다 새로 붙는 번호다.
- **DB 캐시**: 같은 법령을 다시 조회할 때 법제처를 다시 부르지 않고 DB에서 바로 응답한다. 호출량 제한과 트래픽을 아끼고 응답도 빠르다. 조회 시각(`fetched_at`)이 쌓이므로 이력도 남는다. 캐시는 읽기(`load_law`)와 쓰기(`save_law`)가 짝을 이뤄야 동작한다.

## 응답 구조 확인 기록 (explore.py)

- 목록조회 응답은 `LawSearch → law[]` 구조이고, 한 항목에 키가 16개 있다(`법령명한글`, `법령ID`, `법령일련번호`, `시행일자`, `소관부처명` 등).
- `법령일련번호`(290247)는 항목 위쪽에, `법령ID`(010199)는 그보다 열 줄쯤 아래에 있다. `법령상세링크`의 `MST=` 값이 법령일련번호다.
- 본문조회 응답은 `법령 → 조문 → 조문단위[]` 구조이다. `조문내용`에는 조문 제목과 첫 문장만 들어 있고, 항·호는 별도 배열에 있다.
